Entropy is a term from physics that refers to the amount of "disorder" in a system. While software development is immune to all physical laws, the inexorable increase in entropy is inevitable.

When disorder increases in software, we call it "software rot" or "technical debt".

There are many things that can contribute to this "software rot". But there are ways to handle it effectively of course.
## Don't Live With Broken Windows
Don't leave "broken windows" e.g. bad designs, wrong decisions, or poor code linger for too long.

Fix it as soon as it's discovered to stop further damage and if there's not enough time to repair it, then board it up e.g. commenting out the offending code or displaying a "Not implemented" message or substitute dummy data etc.

Neglect accelerates "software rot" much faster compared to any other factor.

And don't cause collateral damage simply because there's a crisis of some sort. One "broken window" is one too many and is all it takes to start the decline. If you find yourself working on a project with quite a few "broken windows" it's all too easy to slip into the mindset that "All the rest of this code is crap. I'll just follow suit."

On projects that are well written and the code is beautiful, a programmer will take extra special care not to mess things up and keep it pristine. Similarly, if the project is not well written with "broken windows" and such, a programmer will care less about writing proper code which will inflict additional damage and contribute to the "software rot".

So never tolerate "broken windows" and take care of them as soon as possible.
